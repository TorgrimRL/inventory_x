# Customer Testing README – InventoryX

## Purpose

This customer test was conducted to evaluate **InventoryX**, a web-based inventory management application for small
businesses. The purpose of the test was to assess whether real users could complete important day-to-day inventory tasks
in a realistic context of use, and whether the product was useful, usable, and relevant for the business. This focus
follows the idea that customer testing should gather feedback on a product’s **features**, **usability**, and **fit to
the customer’s business**, while scenario-based and acceptance-oriented testing should reflect how customers actually
use the product.

## Why this test focused on these workflows

This test focused on the workflows that are most central to InventoryX as an inventory system: accessing the correct
business inventory, viewing stock quickly, adding and editing items, updating stock after sales or deliveries,
registering damaged items, identifying low-stock situations before products run out, and controlling access between
owners and employees. This focus was chosen because user stories and scenarios are meant to describe what users want to
do with a product in natural language, and testing should therefore be centered on realistic tasks rather than only
abstract opinions about the system.

## Business contexts used in testing

The customer testing was carried out in **two business contexts**: one session in a **bookstore** context and one
session in a **cookie shop** context. The reason for doing this was to evaluate the same InventoryX workflows in two
slightly different small-business settings without changing the overall test method. In both cases, the goal was still
to examine whether the implemented features supported real work tasks in a way that felt useful and practical to the
participant.

## Why we used SUS

To document the usability part of the test in a structured way, we used the **System Usability Scale (SUS)**. MeasuringU
describes SUS as a **10-item questionnaire with 5 response options**, used after usability testing to capture perceived
usability, and explains the standard 0–100 scoring method. We used it because it is short, standardized, and widely
used, which makes it suitable as a structured follow-up after the task-based part of the customer
test.

## How the test was carried out

Each participant completed the task set that matched their role in InventoryX, either **Owner** or **Employee**. One
test session was run in a bookstore scenario and one in a cookie-shop scenario. During the session, we documented the
expected outcome, the actual outcome, whether the task was completed, and any observed issues or comments. After the
task-based part, the participant gave short feedback on features, usability, and business fit, and then completed the
SUS questionnaire. This combines scenario-based customer testing with a standardized usability
measure.

## What was documented

The test documentation records session information, business context, the tasks performed in InventoryX, expected and
actual outcomes, observed issues, participant feedback, and the SUS result. This was done to create a structured record
of both what the participant could do in the system and how the system was experienced overall.  ([MeasuringU][1])

## How to use this document

For each customer test session, create a new copy of the **Customer Testing Record** and complete it separately. One
record should be used for each participant and each test session so that results, issues, and SUS scores are documented
individually.
